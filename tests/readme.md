# tests

Два инструмента для проверки кода бота **без сервера, Telegram и докера**.

Оба поднимают настоящий класс `Bot` со всеми трейтами, но:

* сеть и SSH заглушены (`request()`, `ssh()`, `send()`, `update()` — пустышки);
* абсолютные пути (`/config`, `/logs`, `/certs`, `/ssh`, `/update`) подменяются
  на временный каталог, поэтому ни настоящий конфиг, ни ключи не трогаются;
* конфиг собирается синтетический, в двух вариантах — см. «профили» ниже.

Ничего запускать на сервере не нужно и не стоит: это инструмент разработки.
`scripts/init.sh` исключает эту папку из рабочей копии на сервере
(`git sparse-checkout`), так что там её не будет.

## Профили конфига

| профиль | что это |
|---|---|
| `full` | обжитый сервер: домен, SSL, два пользователя, списки, статистика |
| `fresh` | только что поставленный бот: нет ничего, что создаётся по ходу работы |

`fresh` важнее, чем кажется: большинство ошибок вида «нет такого ключа»
вылезает именно на свежей установке, где ключей ещё не существует.

**Фикстура `fresh` обязана быть честно пустой.** Первый же боевой прогон это
доказал: стенд создавал `config.php` с ключом `debug`, секреты mtproto и файл
статистики — то есть проверял более обжитую установку, чем бывает сразу после
`init.sh`. В результате `if ($c['debug'])` в `index.php` давал предупреждение
**на каждый HTTP-запрос** в бою и ни одного на стенде. Если добавляете в
фикстуру файл или ключ — сначала проверьте, что он там вообще бывает у
свежепоставленного бота.

По той же причине в сценарии входят **точки входа**, а не только методы
трейтов: `index.php` грузит `bot.php` сам, поэтому обрабатывается отдельной
веткой (до загрузки классов) — иначе получилось бы повторное объявление
`class Bot`. Именно оттуда и шёл весь шум в логе.

## `e_all.php` — поиск скрытых ошибок

```bash
php tests/e_all.php
```

Гоняет ~40 сценариев (выдача подписки во всех форматах, меню пользователя,
списки, шаблоны, задачи cron, бэкап/восстановление, WARP, DNSTT, MTProto) на
обоих профилях под `error_reporting = E_ALL` и печатает все предупреждения с
точным файлом и строкой.

Зачем: в PHP 8 «файл не прочитался», «нет ключа в конфиге» и «переменная не
объявлена» — это warning'и. В бою они уходят в `/logs/php_error`, но проще
поймать их здесь, до выката.

Ожидаемый результат — чисто. Исключение: на Windows останутся три строки про
`/proc/stat` и `/proc/meminfo` (в Linux-контейнере эти файлы есть).

Если локальная сборка PHP без `mbstring`/`intl`/`yaml`/`curl` — стенд
подставляет заглушки, чтобы сценарии доходили до конца, а не падали на первом
же вызове.

## `compare_behaviour.php` — проверка, что ничего не сломалось

Снимает «отпечаток» поведения: для 22 функций сохраняет возвращаемое значение,
напечатанный вывод и все сообщения, которые бот отправил бы. Сравнив отпечатки
до и после правки, видно, изменилось ли поведение — и где именно.

Особенно полезно для массовых механических правок (расстановка `??`,
переименования), где глазами диф не проверишь.

```bash
# снимок текущего состояния репозитория
php tests/compare_behaviour.php . full > /tmp/after.json

# снимок предыдущего коммита
mkdir /tmp/before && git archive HEAD~1 | tar -x -C /tmp/before
php tests/compare_behaviour.php /tmp/before full > /tmp/before.json

diff /tmp/before.json /tmp/after.json
```

Каждый скрипт печатает результат после маркера `@@OUT@@` / `@@JSON@@` —
вырезать можно любым способом, например `sed 's/^.*@@OUT@@//'`.

Пути песочницы попадают внутрь конфигов sing-box, а они у двух копий разные —
при сравнении их надо нормализовать, иначе будет ложное различие:

```bash
sed -i -E 's/sbbot_cmp_[0-9a-f]{32}/SANDBOX/g' /tmp/before.json /tmp/after.json
```
