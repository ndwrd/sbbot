# SBBOT — руководство пользователя/админа

## Привязка своей группы outbound к конкретному серверу (`~{тег}:outbounds~`)

Если в своём кастомном шаблоне подписки (sing-box, mihomo; xray — пока
по-старому, ждёт своей очереди) нужна отдельная группа, которая ходит только
через определённый сервер (например, отдельный `urltest`/`url-test` для
конкретного сайта через ноду в нужной стране) — используйте плейсхолдер
`~{тег сервера}:outbounds~`.

**1. Узнать тег сервера.**
- Бот: Menu -> Sing-box — там строка `Outbound tag: ~🇩🇪DE:outbounds~` (тег
  считается один раз при первой генерации подписки и больше не меняется).
- Нода: Menu -> Nodes -> нужная нода — там же строка `Node outbound tag:
  ~🇷🇺RU:outbounds~`.

Тег — это флаг + код страны, тот же, что уже виден в реальных outbound'ах
(`🇷🇺RU|Vless` → тег `🇷🇺RU`). Если у нескольких серверов совпадает страна, у
второго и далее — цифра: `🇷🇺RU2`, `🇩🇪DE3` и т.д.

**2. Вписать `~{тег}:outbounds~`** как элемент массива `outbounds` (sing-box)
или `proxies` (mihomo) в своей группе шаблона. На сборке подписки он
разворачивается в реальные теги протоколов этого сервера — Vless/Naive/
Hy2/Anytls у sing-box, Vless/Hy2/Anytls у mihomo (naive там не
поддерживается).

Sing-box, пример — группа "Youtube" только через ноду RU:
```json
{
    "type": "urltest",
    "tag": "Youtube",
    "outbounds": ["~🇷🇺RU:outbounds~"],
    "url": "https://www.gstatic.com/generate_204",
    "interval": "5m"
}
```

Mihomo, тот же смысл:
```json
{
    "name": "Youtube",
    "type": "url-test",
    "proxies": ["~🇷🇺RU:outbounds~"],
    "url": "https://www.gstatic.com/generate_204",
    "interval": 300
}
```

Можно смешивать с обычными тегами в том же массиве:
`"outbounds": ["~🇷🇺RU:outbounds~", "~🇩🇪DE:outbounds~"]` или
`["~🇷🇺RU:outbounds~", "🇩🇪DE|Vless"]`.

Если сервер в момент генерации подписки недоступен/выключен/не
синхронизирован — `~{тег}:outbounds~` просто пропадает из списка (группа
останется с меньшим числом участников), конфиг не ломается. Если из группы
пропали **все** участники, в неё подставляются протоколы Бота — пустую группу
не принимают ни sing-box, ни mihomo, — и трафик группы временно идёт через
Бота, пока сервер не вернётся.

Нода не попадает в подписку, пока на неё не доставлен список пользователей
(флаг синхронизации). Если при изменении пользователей нода не ответила, бот
сам повторяет синхронизацию раз в 30 секунд, как только нода снова на связи —
нажимать «Sync users» вручную не нужно.

**Только** ноды, которых нет ни в одной группе шаблона явно, попадают в
основную группу по умолчанию (`Proxy` — и в sing-box, и в mihomo), без
всякого плейсхолдера. В sing-box это `selector` со вложенной `⚡️Auto`
(`urltest`) — исключение затрагивает обе сразу; в mihomo отдельной
auto-группы нет — сам `Proxy` уже `type: fallback` и сам умеет
health-check-выбор.

Нода, упомянутая через `~{тег}:outbounds~` хотя бы в одной кастомной
группе шаблона, **исключается** из `Proxy`/`⚡️Auto` (fallback у mihomo) —
она доступна только там, где её явно указали. Определяется автоматически
по факту упоминания плейсхолдера где-либо в шаблоне — никакой отдельной
пометки типа "exclude" ставить не нужно, и легко забыть было бы нечего.

## Домены Бота и нод

У каждого сервера должно быть своё имя. Если задать ноде домен Бота, работать
это не будет: имя резолвится в один IP, поэтому клиенты ноды придут на Бота, а
на самой ноде не выпустится сертификат — проверка Let's Encrypt уйдёт не на тот
сервер. Бот такой домен не примет и предложит поддомен.

Рабочая схема — Бот на домене, ноды на поддоменах:

| сервер | имя | A-запись |
|---|---|---|
| Бот | `example.com` | IP Бота |
| нода RU | `ru.example.com` | IP ноды |
| нода DE | `de.example.com` | IP ноды |

Поддомены naive и anytls каждый сервер генерирует себе сам от своего имени, и
сертификат на ноде выпускается тоже на её собственные имена. Отдельный домен
для ноды тоже подходит — важно лишь, чтобы имена не пересекались.

Проще всего вообще не заводить домен: кнопка `nip.io` даёт ноде имя из её же
IP, и DNS настраивать не нужно.

## Списки правил (ruleset)

Готовый список доменов или подсетей подключается ссылкой: Menu -> Sing-box ->
Маршруты -> Списки правил. Формат строки:

```
политика[:behavior]:интервал:URL
```

- **политика** — куда отправлять совпавшее: имя группы из шаблона (`Proxy`,
  `🎥YouTube`) или встроенное значение (`reject`, `direct`). Имя пишется как
  есть: mihomo сверяет его точно, `PROXY` и `Proxy` — разные политики.
- **behavior** — только для mihomo: `domain`, `ipcidr` или `classical`.
- **интервал** — как часто клиент обновляет список: для sing-box — длительность
  с единицей (`72h`, `24h`), для mihomo — секунды (`86400`).

Формат файла определяет, в какую подписку попадёт список:

| подписка | файл | пример |
|---|---|---|
| sing-box | `.srs` | `Proxy:72h:https://github.com/MetaCubeX/meta-rules-dat/raw/sing/geo/geosite/youtube.srs` |
| mihomo | `.mrs`, `.yaml`, `.yml` | `🎥YouTube:domain:86400:https://github.com/MetaCubeX/meta-rules-dat/raw/meta/geo/geosite/youtube.mrs` |
| mihomo, блокировка | `.mrs` | `reject:domain:86400:https://github.com/MetaCubeX/meta-rules-dat/raw/meta/geo/geosite/category-ads-all.mrs` |

Один и тот же список для обоих клиентов добавляется двумя строками — по одной
на формат. Блокировки (`reject`) встают в начало списка правил, остальные — перед
последним правилом.

Особенность sing-box: политика должна совпадать с outbound у правила с
`addruleset` в шаблоне — в стандартном это `Proxy` и блокировка. Своя группа
подойдёт, только если вы добавили для неё такое правило в шаблон. В mihomo
ограничения нет: подойдёт любая группа из `proxy-groups`.

Если политики с таким именем в шаблоне нет, правило выбрасывается из подписки —
пропадёт только оно, а конфиг останется рабочим.

В подписке список получает короткое имя `политика:вид/файл` — его видно в логах
и интерфейсе клиента: `Proxy:geosite/telegram` и `Proxy:geoip/telegram` —
списки доменов и адресов с одинаковым именем файла. Вид берётся из каталога
`geosite`/`geoip` в адресе, у mihomo — из behavior (`domain` → geosite, `ipcidr`
→ geoip). Не определился, а имя файла повторяется — вместо вида каталог из
адреса, совпало и так — номер: `block:main/ads#2`.

Собственные списки бота (домены, подсети, блокировки, Warp и т. п.) клиент
обновляет раз в час: правка в боте доходит до клиентов в течение часа.

## Telegram Proxy: MTProto и Web Proxy

Прокси работает на [Telemt](https://github.com/telemt/telemt) — активно
развиваемой реализации MTProxy, которая умеет и обычный MTProto, и WEB-прокси.
Управление: Menu -> Telegram Proxy. В тексте — блоки MTProto и Web Proxy
Бота, под ними такие же по каждой ноде; кнопки сгруппированы под
заголовками «MTProto» и «Web Proxy».

- **Секрет** — «Сгенерировать» или «Установить свой». Можно вставить и готовую
  `ee…`-строку из ссылки: лишний префикс и хвост-домен бот отбросит сам. Ввод
  `0` вместо секрета останавливает прокси; «Сгенерировать» или новый секрет
  запускают его снова.
- **Fake-домен** — имя, под которое маскируется соединение (`ee`-режим). Авторы
  mtproto.zig и фиксов MEKO независимо друг от друга предупреждают: с июня 2026
  домен должен поддерживать X25519MLKEM768, иначе клиентов на iOS помечают.
  Проверить можно так (нужен OpenSSL 3.5+):
  `openssl s_client -groups X25519MLKEM768 -connect домен:443`.
- **Ссылка и QR** — для клиента; порт берётся из настроек портов.

Как применяются изменения:

- **секрет** — на лету: Telemt сам перечитывает конфиг, соединения не рвутся;
- **fake-домен** — перезапуском контейнера: у клиентов MTProto короткий обрыв,
  после которого они переподключаются сами.

**WEB-прокси** — тот же MTProto, но клиент ходит к
серверу настоящим HTTPS через встроенный браузер. На проводе нет
FakeTLS-рукопожатия и TLS-отпечатка клиента Telegram — главного, по чему сейчас
распознают MTProxy. Кнопки под заголовком «Web Proxy» устроены как у MTProto:
«Сгенерировать ключ» или «Установить свой ключ» включают WEB с этим ключом
(если уже включён — только меняют ключ, на лету), ввод `0` вместо ключа —
выключает, «Показать QR» — QR ссылки:

- нужен домен с сертификатом Let's Encrypt — самоподписанный клиент не примет.
  Для WEB бот заводит случайный поддомен. В сертификат он попадает сам при
  выпуске SSL, если его DNS уже указывает на сервер: у `nip.io` — всегда, у
  своего домена — когда A-запись поддомена совпадает с основным доменом.
  Тогда включение WEB обходится без перевыпуска. Если поддомена в сертификате
  ещё нет (сертификат выпущен раньше, чем появилась A-запись, или до этой
  версии), бот один раз перевыпустит его при включении WEB и предупредит об
  этом. Нет A-записи — WEB сразу откажет и попросит её добавить, не трогая
  сертификат;
- поддомен виден в Настройки -> Домены (строка «Telegram Proxy»); при
  установке своего домена бот сразу называет его среди имён для A-записей;
- ссылка вида `https://t.me/webproxy?server=…&secret=dd…`, порт в ней не
  указывается — всегда 443;
- у WEB свой ключ, обычный MTProto его смена не трогает;
- удаление домена выключает WEB — включите заново после установки нового;
- включение и выключение WEB перезапускают контейнер прокси — короткий обрыв
  обычного MTProto;
- на нодах — так же: Ноды -> нода -> Telegram Proxy. Нужен домен ноды с
  сертификатом Let's Encrypt; поддомен ноды виден в её «Домены и порты», а
  при установке своего домена бот называет его среди имён для A-записей.
  «Показать QR» у Web Proxy в меню Бота присылает QR Бота и всех нод, где WEB
  включён. Нода должна быть обновлена — иначе бот сообщит, что она не ответила.

Режим работы — через middle-proxy Telegram. Это осознанный выбор: в прямом
режиме (без middle-proxy) у аккаунтов без Premium не грузятся фото, видео и
истории.

Конфиг Telemt (`config/telemt/config.toml`) целиком пишет бот — править его
руками бессмысленно, при следующем изменении он перезапишется. Версия образа
зафиксирована в `docker-compose.yml` и поднимается вместе с обновлением бота.

Логи прокси — в общем списке: Настройки -> Логи -> MTProto (у нод — в их меню
логов). Они лежат не файлом, а в контейнере (образ пишет в stdout), поэтому у
этого пункта нет размера и кнопки очистки — ротацией занимается docker. Из
консоли: `make tg`.

**Переход с teleproxy** (прежний образ) происходит сам при обновлении: секрет,
fake-домен и порт переносятся как есть, поэтому ссылки у клиентов остаются
прежними. Ноды переходят так же — кнопкой «Обновить» в карточке ноды.

## Блок статуса в главном меню

Блок вверху главного меню Бота (и такой же в карточке ноды):

```
🟢 Sing-box        🟢 443
🟢 Telegram Proxy  🟢 4443
🟢 Warp
```

- **Sing-box** — запущен ли процесс sing-box; справа — порт 443.
- **Telegram Proxy** — работает ли контейнер прокси Telegram (один на MTProto и
  Web Proxy); справа — порт MTProto. «port unavailable» — порт не опубликован
  наружу. У Web Proxy своего порта нет: он идёт через общий 443.
- **Warp** — проходит ли запрос через туннель Warp до Cloudflare.
- **dnstt** — появляется после первой настройки dnstt; справа — порт 53.

Статусы собирает cron примерно раз в 10–15 секунд, меню показывает последний
результат. Карточка ноды на Боте обновляется раз в 30 секунд.

**Warp проверяется иначе**: запрос идёт через сам туннель и на канале с
потерями пакетов может занимать несколько секунд. Поэтому Warp проверяется раз
в минуту с таймаутом 10 секунд, а красным становится только после двух
неудачных проверок подряд — то есть если Warp не отвечает около двух минут.
Одна медленная попытка статус не меняет. Warp+ (ответ `warp=plus`) считается
рабочим, как и обычный.

Проверить Warp вручную (на Боте или ноде):

```bash
cd ~/sbbot && docker compose exec -T sbx curl -s -m 20 -x socks5://wp:1080 -w "tls=%{time_appconnect} total=%{time_total}\n" https://cloudflare.com/cdn-cgi/trace | grep -E "warp|colo|tls"
```

`warp=on` или `warp=plus` — работает; `tls` — сколько занял путь через туннель.
Состояние самого туннеля: `docker compose exec wp wg show` — строка
`latest handshake` должна быть не старше двух-трёх минут.

## Защита от сканирования и блокировка адресов

**Ограничение частоты запросов** — в nginx, 5 запросов в секунду на адрес со
всплеском до 10:

```
limit_req_zone $binary_remote_addr zone=decoy:10m rate=5r/s;
limit_req zone=decoy burst=10 nodelay;
```

- применяется только к сайту-обманке; подписки, WebApp и клиентский трафик под
  ограничение не попадают;
- считается в памяти, на диск ничего не пишется;
- превысивший темп получает отказ на конкретные запросы и продолжает работать —
  навсегда никто не блокируется.

**Закрыть конкретный адрес** можно вручную: `config/deny` подключён в
`upstream.conf` внутри `stream {}` и действует на TCP-соединения к 443. Бот в
этот файл не пишет.

Обе команды выполняются из каталога бота (`~/sbbot` при установке скриптом из
readme): путь к файлу относительный, а `docker compose` без compose-файла рядом
не запустится.

```bash
cd ~/sbbot
echo "deny 1.2.3.4;" >> config/deny
docker compose exec up nginx -s reload
```

Синтаксис — как у nginx, поэтому так же закрывается и целая подсеть. Это
обычный случай: сканеры ходят не с одного адреса, а со всего блока провайдера,
и в `logs/nginx_error` тогда видно десятки строк `limiting requests` с соседних
адресов вида `45.148.10.123`, `45.148.10.60`, `45.148.10.21`.

```bash
cd ~/sbbot && echo "deny 45.148.10.0/24;" >> config/deny && docker compose exec up nginx -s reload
```

Пустой файл (по умолчанию) ничего не ограничивает.

## Трафик пользователей: Бот и ноды

Трафик пользователя — сумма по всем серверам: Бот плюс все ноды. Сумма
используется везде: в списке пользователей, в карточке пользователя, на
странице подписки, в заголовке `subscription-userinfo` и в проверке лимита
трафика.

В карточке пользователя под ссылкой Subscription — итог и разбивка по
серверам: Бот первым, дальше ноды в порядке списка «Ноды», серверы без
трафика этого пользователя — с нулями:

```
Traffic: ↓12.3 GB ↑1.1 GB
🇳🇱NL (Бот): ↓8.0 GB ↑0.7 GB
🇷🇺RU BG: ↓4.0 GB ↑0.3 GB
🇩🇪DE SRT: ↓0 B ↑0 B
```

- Бот забирает трафик с нод раз в 5 минут; нода, которая недоступна,
  сохраняет последние известные цифры.
- «Сбросить статистику» — у пользователя или у всех, в том числе ежемесячный
  сброс — сбрасывает и на нодах. Нода не ответила — сброс повторится, когда
  она снова будет на связи; до этого её цифры в сумму не входят.
- Ноды должны быть обновлены: на старой версии нода трафик не отдаёт.

## Трафик и срок в клиентах mihomo

Подписка mihomo отдаёт заголовок `subscription-userinfo`: Clash Verge и
похожие графические клиенты показывают по нему в карточке профиля
потраченный трафик, лимит и срок действия. Приложение sing-box его не читает.

- трафик — тот же, что бот считает для лимита и показывает на странице
  подписки: Бот и ноды вместе (см. «Трафик пользователей: Бот и ноды»);
- лимит — только если он задан пользователю («Установить лимит»); без него
  клиент покажет один потраченный трафик;
- срок — только если задано время действия («Установить время действия»).

Цифры обновляются вместе с подпиской: раз в 6 часов или по кнопке обновления
в клиенте.

## Подписка для Happ / INCY

В отличие от xray/sing-box/mihomo, Happ и INCY не грузят наш JSON как
конфиг ядра — у них свой движок и свой формат. Подписка (`t=hp`) отдаёт:

- **Тело** — просто список `vless://`/`hysteria2://` ссылок (base64), по
  одной паре на каждый готовый сервер (main + ноды), с тем же
  `{flag}{geoTag}|` префиксом в имени, что и у sing-box/mihomo.
- **Роутинг** — отдельным HTTP-заголовком `routing:
  happ://routing/onadd/<base64 JSON>` на том же ответе. База —
  `config/happ_routing.json` (адаптированный lite-профиль
  [DigneZzZ/routing](https://github.com/DigneZzZ/routing), `Geositeurl`/
  `Geoipurl` смотрят на их CDN), поверх которого `buildHappRouting()`
  дописывает пользовательские списки бота: `blocklist` → `BlockSites`,
  `includelist`+`warplist` → `ProxySites`, `subnetlist` → `ProxyIp`.

У INCY есть задокументированный deep-link на "добавить подписку в один
тап" — `incy://add/<url>` (обычная, не закодированная ссылка). У Happ
такого нет — подписка добавляется вставкой обычной ссылки/QR в форму
приложения; поэтому Happ и убран из подборки приложений на странице
подписки (см. ниже), остался только INCY.

*Routing*-профиль можно активировать в один тап у обоих:
`happ://routing/onadd/<base64>` / `incy://routing/onadd/<base64>` —
задокументированные deeplink-схемы каждого приложения (разные, поэтому
и base64 у них общий, а схема — своя). На странице подписки это кнопка
«Активировать роутинг» рядом со «Скачать»/«Добавить» в карточке INCY —
открывает приложение и сразу активирует/перезаписывает профиль, не
дожидаясь ближайшего обновления подписки (когда профиль и так придёт
через HTTP-заголовок `routing:`). `happ://routing/onadd/...` в `sub()`
больше не собирается — если Happ когда-нибудь вернётся в подборку,
собрать его обратно из уже готового `buildHappRouting($pac)` — одна
строка.

## Страница подписки (`t=hp` → `/pac{hash}/sub?id=...`)

Клиентская HTML-страница (`app/subscription.php`) рендерит статус,
список серверов, ссылки для ручного добавления и подборку приложений по
платформам (iOS/Android/Windows/macOS) с кнопками «Скачать»/«Добавить».

**Список приложений** — в `app/apps.json` рядом с `subscription.php`.
Формат на платформу — массив объектов:
```json
{"name": "sing-box", "icon": "📦", "hint": {"ru": "...", "en": "..."},
 "download": "https://...", "add": "singboxImport"}
```
`add` — не готовая ссылка, а символическое имя схемы (`singboxImport`,
`incyAdd`, `rabbitholeAdd`, `mihomoImport`, `onexraySubAdd`), которое
`resolveAppAddLink()` в `subscription.php` разворачивает в реальный
deep-link с нужным urlencode из уже посчитанных данных подписки. `add:
null` — только кнопка «Скачать», для приложений без документированной
диплинк-схемы one-tap добавления (добавить конфиг можно только руками).

`icon` — не эмодзи, а имя файла в `app/webapp/icons/<icon>.png` (128×128,
отдаётся nginx статикой без хэша, `/webapp/icons/...`). Чтобы добавить
новую иконку — просто положить туда png с нужным именем и сослаться на
него по этому имени из `apps.json`/`apps.override.json`.

`downloadKey` (опционально) — для GitHub-релизов, где версия зашита в имя
файла ассета (типа `SFW-1.14.0-x64.exe`) и поэтому обычный
`releases/latest/download/<файл>` не работает. `checkAppDownloadLinks()`
в `BotCoreTrait.php` раз в сутки (через общий `cron()`) дёргает
`api.github.com/repos/.../releases/latest`, находит ассет по regex-шаблону
имени и кэширует прямую ссылку в `/config/apps_cache.json` (не трекается).
`resolveDownloadLink()` в `subscription.php` берёт свежую ссылку оттуда,
если она есть, иначе остаётся на статическом `download` из `apps.json`
(обычно — страница `releases/latest`, чтобы не было 404 до первого прогона
кэша). Новые GitHub-приложения с версией в имени файла добавляются в
список `$targets` внутри `checkAppDownloadLinks()`.

**Кастомизация переживает `git pull`** — как и `i18n.override.php`:
- `app/apps.override.json` — если существует, его платформы (`ios`,
  `android`, ...) полностью подменяют одноимённые в `apps.json`
  (`array_merge` по ключу платформы, не глубокое слияние по приложениям).
- `app/subscription.override.php` — если существует, используется вместо
  всего `subscription.php` целиком (для более глубокой переверстки
  страницы).

Оба override-файла в `.gitignore`, сам `subscription.php`/`apps.json` —
трекаются и обновляются вместе с ботом.

## Обновление бота и origin-шаблоны

Origin-шаблоны (Шаблоны → Origin) — это файлы `config/sing.json`,
`config/clash.json`, `config/xray.json`, рядом серверный
`config/sing-server.json`. Что с ними будет, зависит от способа обновления:

- **кнопкой** «update bot» (и автообновлением) — шаблоны не меняются: перед
  обновлением бот делает бэкап и после перезапуска возвращает их из него.
  Правки сохраняются, но и новые шаблоны из релиза не приходят;
- **из консоли** (`echo 1 > update/pipe` или `make c && git pull`) — шаблоны
  заменяются версиями из репозитория: приходят новые, правки теряются.

Обновиться из консоли, сохранив свои шаблоны:

```bash
cd ~/sbbot && mkdir -p /root/origin_keep && cp config/sing.json config/clash.json config/xray.json config/sing-server.json /root/origin_keep/ && make c && git pull && cp /root/origin_keep/*.json config/ && make r
```

## Переезд с vpnbot

Бэкап vpnbot восстанавливается в sbbot так же, как собственный: бот сам
узнаёт формат и переносит то, чему в sbbot есть место.

1. В vpnbot: настройки → **сохранить** — бот пришлёт файл бэкапа.
2. Поставьте sbbot на новый сервер (см. [readme.md](readme.md)) и напишите
   ему `/start` — первый написавший станет админом. Админы в бэкап не
   входят ни у vpnbot, ни у sbbot.
3. В sbbot: Настройки → **Восстановить** — и ответьте на сообщение файлом
   бэкапа vpnbot.

**Переносится:**
- сертификат домена, MTProto (секрет, fake-домен, adtag), DNSTT (ключи,
  домен, пароль);
- домен, `hashbot`, язык (если в sbbot есть такой перевод), размер
  страницы, автообновление, автобэкап, автосброс статистики, автоочистка
  логов, лицензия WARP+;
- списки маршрутизации: через прокси, блок, warp, подсети, процессы,
  пакеты, rule-set'ы;
- пользователи: имя (`email`) становится описанием, uuid, срок и
  вкл/выкл сохраняются. username и пароль генерируются новые. Пользователь
  с уже существующим uuid пропускается — повторный импорт дублей не даст.

**Не переносится:** WireGuard/AmneziaWG, AdGuard, OpenConnect, Shadowsocks,
отдельный Hysteria, привязка устройств (HWID), лимиты IP, статистика
трафика, шаблоны подписок, Reality-ключи и транспорт — у sbbot свои.

**После переноса:**
- **Ссылки подписки vpnbot продолжают работать**, если домен остался
  прежним: формат ссылки у ботов общий (`/pac{hash}/…` с uuid внутри), а
  `hashbot` и uuid переносятся. Клиент при следующем обновлении подписки
  сам получит конфиг sbbot.
- **Прямые `vless://`-ссылки и QR из vpnbot работать перестанут** —
  транспорт, Reality и пароли naive/hysteria2/anytls теперь от sbbot. Таким
  клиентам нужно выдать ссылку заново.
- **Домен nip.io** сам перестроится под IP нового сервера, сертификат
  перевыпустится автоматически. Но домен при этом меняется, поэтому старые
  ссылки подписки перестанут открываться — клиентам нужно добавить
  подписку заново.
- **Свой домен:** сертификат из vpnbot покрывает только сам домен, без
  поддоменов naive и anytls, которых у vpnbot нет. В конце импорта бот
  пришлёт список имён — направьте их DNS A-записи на IP нового сервера и
  перевыпустите сертификат: Настройки → Domains → **Letsencrypt SSL**.
